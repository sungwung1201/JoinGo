# 📂 JoinGo Web Dashboard 디버깅 및 개선 히스토리 (`Web / Integration`)

프로젝트 진행 과정에서 JoinGo 웹 대시보드는 단순 모니터링 화면에서 출발하여, Firebase Realtime Database, 3D Scan Viewer, RGB 영상 탭, 예외 상황 처리, 나사별 상세 로그, 불량 해결 처리까지 포함하는 통합 관제 웹으로 발전했습니다.

본 문서는 KJH가 담당한 Web / Integration 파트의 주요 문제, 디버깅 과정, 해결 방식, 최종 구조를 정리한 웹 전용 `DEBUGGING.md`입니다.

> **기간**: 2026년 5월 20일 ~ 2026년 5월 26일  
> **담당**: KJH  
> **파트**: Web / Integration  
> **핵심 범위**: Firebase Realtime Database 연동, 3D Scan Viewer 통합, Point Cloud 렌더링 최적화, 예외 상황 GUI, RGB 영상 탭, 나사 상세 로그 팝업, 웹 UI/UX 개선

## 1. 초기 JoinGo 모니터링 웹 구축 단계  
### Firebase DB 기반 상태 표시 구조 설계 `(5.20)`

초기 웹페이지는 로봇·비전·DB가 생성한 검사 결과를 사용자가 웹 화면에서 확인할 수 있도록 하는 단순 모니터링 화면에서 시작했습니다.

- **작업 범위**
  - JoinGo 웹 대시보드 개발 방향 설정
  - Firebase Realtime Database와 웹 GUI 연동 방식 검토
  - 검사 상태, 나사 상태, 불량 로그를 웹 카드 형태로 표시
  - 웹에서 Firebase로 명령을 전송하는 구조 검토

- **이슈 및 디버깅**
  - 검사 결과가 DB에는 존재하지만, 사용자가 웹에서 현재 상태를 직관적으로 확인하기 어려웠습니다.
  - 어떤 DB 경로를 웹에서 직접 구독해야 하는지 명확하지 않아, 화면 표시용 데이터와 내부 처리용 데이터를 구분해야 했습니다.
  - Firebase config가 없을 경우 실제 DB 연결이 되지 않으므로, 로컬 데모와 실제 연결 상태를 구분할 필요가 있었습니다.

- **해결 및 개선 로직**
  - Firebase config 적용 후 Realtime Database의 주요 경로를 읽는 구조를 구현했습니다.
  - 검사 상태, 나사 상태, 불량 로그를 카드형 UI로 분리하여 표시했습니다.
  - 웹에서 로봇 또는 서버 측으로 명령을 전달할 수 있도록 command 경로 사용 가능성을 검토했습니다.
  - 로컬 실행을 위해 `python -m http.server 5500` 방식으로 HTML 파일을 테스트할 수 있게 정리했습니다.

- **결과**
  - 웹페이지가 단순 정적 화면이 아니라 Firebase DB를 실시간으로 읽는 관제 화면으로 전환되었습니다.
  - 이후 3D Scan, 예외 상황, 나사 상세 로그 기능을 붙일 수 있는 기본 웹 구조가 마련되었습니다.

## 2. 3D Viewer 통합 초기 단계  
### Plotly 기반 Point Cloud와 나사 Marker 표시 `(5.21 ~ 5.23)`

초기 웹 구조에 3D Scan Viewer를 통합하면서, 작업대 배경 Point Cloud와 나사 위치 marker를 함께 표시하는 구조를 구현했습니다.

- **작업 범위**
  - viewer HTML을 메인 웹에 통합하는 방식 검토
  - Plotly 기반 3D Point Cloud 렌더링 구조 확인
  - 3D 작업대 배경과 나사 marker 동시 표시
  - normal / defect 상태에 따른 marker 색상 구분
  - 나사 선택 시 상세 정보 표시 구조 설계
  - 불량 나사 해결 완료 시 DB status를 `normal`로 갱신

- **이슈 및 디버깅**
  - 기존 viewer HTML이 메인 웹과 분리되어 있어, 화면 전환 및 데이터 공유가 매끄럽지 않았습니다.
  - iframe 방식으로 붙일 경우 화면은 표시할 수 있지만, 메인 웹의 상태 관리와 직접 연결하기 어려웠습니다.
  - Point Cloud, 나사 marker, 상태값, 상세 로그가 서로 다른 데이터 기준으로 표시되면 사용자가 실제 대응해야 할 불량 위치를 정확히 특정하기 어려웠습니다.
  - DB에서 받은 screw key와 화면에 표시되는 나사 번호가 그대로 연결되면, 사용자가 보는 번호가 0번부터 시작하거나 직관적이지 않을 가능성이 있었습니다.

- **해결 및 개선 로직**
  - iframe 의존도를 줄이고, 메인 웹 내부에서 3D Scan 결과를 직접 표시하는 방향으로 구조를 개선했습니다.
  - Plotly를 사용해 `background_url` 기반 Point Cloud와 screw marker를 같은 3D 화면에 렌더링했습니다.
  - `normal`은 초록색, `defect`는 빨간색 marker로 구분해 시각적으로 불량 위치를 바로 확인할 수 있게 했습니다.
  - 나사 클릭 시 우측 정보 표시 또는 상세 로그 표시가 가능하도록 나사 단위 데이터 구조를 설계했습니다.
  - DB key는 유지하되, 화면 표시 번호는 1번부터 시작하도록 분리 처리했습니다.

- **결과**
  - 3D 화면은 단순 시각화가 아니라, 나사별 상태 확인 및 불량 대응 대상을 선택하는 인터페이스로 확장되었습니다.
  - 사용자는 작업대 위의 나사 위치와 상태를 3D로 확인하고, 특정 나사를 클릭하여 상세 정보를 확인할 수 있게 되었습니다.

## 3. 예외 상황 처리 GUI 구축 단계  
### 비상정지·일시정지·안전정지 상태 표시 및 RESUME 명령 `(5.22)`

로봇 시스템에서는 비상정지, 일시정지, 안전정지와 같은 예외 상황이 발생할 수 있으므로, 웹에서 이를 감지하고 사용자에게 알려주는 기능이 필요했습니다.

- **작업 범위**
  - 예외 상황 처리 GUI 기능 기획
  - `exceptionstatus/current` 경로 구독
  - 비상정지, 일시정지, 안전정지 상태를 웹에서 표시
  - 예외 발생 시 팝업 알림 표시
  - 조치 완료 후 `exceptioncommand`에 `RESUME` 명령 전송
  - `exceptionstatus/history`에 예외 발생 및 재개 이력 기록

- **이슈 및 디버깅**
  - 로봇 또는 서버 측에서 예외 상태가 발생해도 웹 사용자는 현재 시스템이 왜 멈췄는지 즉시 확인하기 어려웠습니다.
  - 단순 상태 표시만으로는 사용자가 조치 완료 후 시스템에 재개 신호를 보내기 어려웠습니다.
  - 예외 발생 이력이 남지 않으면 이후 디버깅이나 발표 시 어느 시점에 어떤 예외가 발생했는지 설명하기 어렵습니다.

- **해결 및 개선 로직**
  - `exceptionstatus/current`를 실시간 구독하여 현재 예외 상태를 웹 UI에 반영했습니다.
  - 예외 발생 시 팝업 알림을 표시하여 사용자가 즉시 인지할 수 있도록 했습니다.
  - 조치 완료 버튼을 통해 `exceptioncommand` 경로에 `RESUME` 명령을 기록하도록 설계했습니다.
  - 예외 발생 및 재개 요청을 `exceptionstatus/history`에 누적 기록하여 후속 분석이 가능하도록 했습니다.

- **결과**
  - 웹이 단순 조회 화면에서 로봇 운용 상태를 감시하고 재개 명령까지 보낼 수 있는 운영 인터페이스로 확장되었습니다.
  - 예외 상황 처리 흐름이 DB를 기준으로 기록되면서, 로봇·서버·웹 간 상태 동기화가 가능해졌습니다.

## 4. 3D Scan 렉 문제 분석 및 렌더링 게이트 적용  
### 실시간 렌더링에서 캡처형 결과 로드 방식으로 전환 `(5.24)`

3D Scan 데이터를 웹에서 실시간으로 계속 렌더링하면, Point Cloud 갱신과 DB 상태 갱신이 동시에 발생하면서 웹 화면에 렉이 발생했습니다. 이 문제를 해결하기 위해 렌더링 방식을 실시간 스트리밍 중심에서 캡처형 결과 로드 중심으로 변경했습니다.

- **작업 범위**
  - 3D Scan 실시간 렌더링으로 인한 웹 렉 문제 확인
  - `3d_scan_done` 완료 신호 기반 렌더링 방식으로 변경
  - 스캔 중에는 3D 화면을 갱신하지 않고 완료 후 한 번만 결과 로드
  - 3D 스캔 미완료 상태에서 작업대 및 샘플링 선택 제한
  - 스캔 미완료 시 "3D 스캔중" 팝업 로그 표시

- **이슈 및 디버깅**
  - 실시간 Point Cloud를 계속 갱신하면 브라우저 렌더링 부하가 커져 웹 반응성이 떨어졌습니다.
  - 스캔 중간 데이터가 계속 화면에 반영되면서 사용자가 완성되지 않은 3D 결과를 선택하는 문제가 발생할 수 있었습니다.
  - 작업대 선택과 샘플링 레이트 변경이 스캔 완료 전에도 가능하면, 아직 로드 가능한 데이터가 없는 상태에서 UI 동작이 꼬일 수 있었습니다.

- **해결 및 개선 로직**
  - `live_scan/3d_scan_done` 값을 확인하여 스캔 완료 여부를 판단했습니다.
  - `3d_scan_done === true`일 때만 작업대 선택과 샘플링 레이트 선택을 허용했습니다.
  - 스캔 중에는 3D 결과를 갱신하지 않고, 완료 신호가 들어온 뒤 캡처형 결과를 한 번 로드하도록 변경했습니다.
  - 스캔 미완료 상태에서 사용자가 작업대 또는 샘플링 옵션을 선택하면 "3D 스캔중" 팝업 로그를 표시했습니다.

- **결과**
  - 3D Scan 데이터를 실시간으로 무리하게 렌더링하지 않게 되어 웹 렉이 완화되었습니다.
  - 사용자는 완성된 스캔 결과만 선택할 수 있어, 잘못된 중간 데이터를 보는 문제가 줄어들었습니다.
  - 웹 UI가 시스템 상태를 기준으로 동작하도록 제어되어 안정성이 향상되었습니다.

## 5. Point Cloud 경량화 및 샘플링 레이트 기능  
### 색상 제거 실패와 색상 샘플링 방식으로의 롤백 `(5.25)`

Point Cloud 렌더링 성능을 높이기 위해 처음에는 색상 정보를 제거하는 방식으로 경량화를 시도했습니다. 하지만 가독성이 떨어지는 문제가 발생하여, 색상 정보를 유지하되 포인트 수를 선택적으로 제한하는 샘플링 방식으로 전환했습니다.

- **작업 범위**
  - Point Cloud 색상 제거를 통한 1차 경량화 적용
  - 색상 제거 후 가독성 문제 확인
  - 색상 샘플링 방식으로 롤백
  - Point Cloud 포인트 수를 선택적으로 제한하는 샘플링 기능 추가
  - 배경 포인트 수 선택 옵션을 1만점부터 5만점까지 1만 단위로 구성

- **이슈 및 디버깅**
  - 색상 정보를 제거하면 렌더링은 가벼워질 수 있지만, 작업대와 나사 주변 환경의 구분이 어려워졌습니다.
  - 3D Scan 화면은 성능뿐 아니라 사용자가 공간 구조를 파악할 수 있는 가시성도 중요했습니다.
  - 모든 상황에서 고정된 Point Cloud 수를 사용하면, 발표 환경이나 PC 성능에 따라 렉이 발생하거나 반대로 디테일이 부족해지는 문제가 있었습니다.

- **해결 및 개선 로직**
  - 색상 제거 방식은 폐기하고, 색상은 유지하되 포인트 수를 제한하는 샘플링 방식으로 변경했습니다.
  - 사용자가 배경 포인트 수를 1만, 2만, 3만, 4만, 5만점 중 선택할 수 있도록 했습니다.
  - 낮은 샘플링은 성능 우선, 높은 샘플링은 가시성 우선으로 사용할 수 있도록 설계했습니다.

- **결과**
  - 사용자는 시스템 성능과 시각적 품질 사이에서 상황에 맞는 값을 선택할 수 있게 되었습니다.
  - 렉 완화와 3D 가독성 사이의 균형을 사용자가 직접 조절하는 구조가 완성되었습니다.

## 6. `viewer_06` 및 `live_scan/workstations` 통합 단계  
### 작업대별 스캔 결과 선택과 최신 작업대 자동 선택 `(5.26)`

최종 웹 구조에서는 viewer_06 구조를 반영하고, `live_scan/workstations` 경로를 기준으로 작업대별 3D Scan 결과를 불러오도록 변경했습니다.

- **작업 범위**
  - viewer_06 구조 반영
  - `live_scan/workstations` 기준으로 웹 통합
  - 작업대별 `section_name`, `timestamp`, `background_url`, `screws` 데이터 로드
  - 작업대 선택 드롭다운 기능 유지
  - 최신 작업대 자동 선택 처리
  - 나사 인덱스를 화면에서 1번부터 표시
  - DB key는 유지하고 화면 표시 번호만 1번부터 시작하도록 분리 처리

- **이슈 및 디버깅**
  - 여러 작업대의 스캔 결과가 존재할 때, 하나의 최신 결과만 표시하면 작업대별 비교나 재확인이 어렵습니다.
  - DB 내부 key와 사용자 화면에 보이는 번호가 다르면, 로봇 또는 DB와의 호환성을 유지하면서도 사용자에게는 직관적인 번호를 보여줘야 했습니다.
  - 최신 작업대를 자동으로 선택하지 않으면, 사용자가 매번 수동으로 작업대를 찾아 선택해야 하는 불편함이 있었습니다.

- **해결 및 개선 로직**
  - `live_scan/workstations` 하위의 작업대 목록을 드롭다운으로 표시했습니다.
  - 각 작업대의 `section_name`, `timestamp`, `background_url`, `screws`를 기준으로 화면을 구성했습니다.
  - 최신 작업대가 존재하면 자동으로 선택되도록 처리했습니다.
  - DB key는 내부 처리용으로 유지하고, 화면에서는 1번부터 시작하는 사용자 친화적 인덱스를 표시했습니다.

- **결과**
  - 작업대별 스캔 결과를 선택해 확인할 수 있게 되었습니다.

## 9. 주요 DB 경로 및 디버깅 기준

| DB 경로 | 용도 | 디버깅 포인트 |
| --- | --- | --- |
| `live_scan/3d_scan_done` | 3D 스캔 완료 여부 판단 | false일 때 작업대·샘플링 선택이 막히는지 확인 |
| `live_scan/workstations` | 작업대 목록 및 3D 검사 데이터 수신 | 작업대 드롭다운 목록이 정상 생성되는지 확인 |
| `live_scan/workstations/{workstation}/background_url` | Point Cloud 배경 데이터 URL | 배경 데이터 로드 실패 시 URL 유효성 확인 |
| `live_scan/workstations/{workstation}/screws` | 나사별 위치, 상태, 시간 정보 | normal/defect marker 색상과 개수 확인 |
| `live_scan/workstations/{workstation}/screws/{screw}/status` | 불량 해결 완료 시 normal로 변경 | 해결 완료 클릭 후 DB 상태값 변경 확인 |
| `live_scan/rgb_stream/url` | RGB 실시간 영상 주소 | 탭 전환 시 영상 URL 로드 여부 확인 |
| `exceptionstatus/current` | 현재 예외 상황 확인 | 예외 상태 발생 시 팝업 표시 여부 확인 |
| `exceptionstatus/history` | 예외 발생 및 재개 이력 기록 | 이벤트 누적 기록 확인 |
| `exceptioncommand` | 웹에서 로봇/서버로 재개 명령 전송 | RESUME 명령 전송 여부 확인 |

## 🎯 프로젝트 회고 및 핵심 역량

본 섹션은 향후 포트폴리오 활용 및 시간이 지난 후에도 프로젝트를 통해 얻은 기술적 인사이트와 성장을 복기하기 위해 작성되었습니다.

### 1. 실시간 처리보다 “완료 기준 데이터”가 더 안정적인 경우가 있다

- **문제 인식**: 3D Scan 데이터를 실시간으로 웹에 반영하면 화면은 즉각적으로 보일 수 있지만, Point Cloud 렌더링과 DB 상태 갱신이 동시에 발생하면서 웹 렉이 심해졌습니다.
- **배움과 극복**: 모든 데이터를 실시간으로 보여주는 것이 항상 좋은 설계는 아니며, 사용자가 실제로 필요한 것은 안정적으로 완성된 스캔 결과라는 점을 확인했습니다. 따라서 `3d_scan_done`을 기준으로 완료된 캡처형 데이터를 로드하는 구조가 더 적합하다고 판단했습니다.

### 2. 성능 최적화는 단순히 데이터를 줄이는 것이 아니라 가독성과 균형을 맞추는 과정이다

- **문제 인식**: Point Cloud 색상 제거는 렌더링을 가볍게 만들 수 있었지만, 작업대와 부품의 공간적 구분이 어려워져 3D Viewer의 의미가 약해졌습니다.
- **배움과 극복**: 색상을 없애는 단순 경량화 대신, 색상은 유지하고 포인트 수를 조절하는 샘플링 구조를 선택했습니다. 이를 통해 성능과 가시성 사이의 균형을 사용자가 직접 조절할 수 있는 방식으로 개선했습니다.

### 3. 웹 UI는 로봇 시스템의 “상태 번역기” 역할을 한다

- **문제 인식**: 로봇, 비전, DB에는 상태 데이터가 존재하지만, 사용자는 raw data만 보고 현재 상황을 이해하기 어렵습니다.
- **배움과 극복**: `normal`, `defect`, `3d_scan_done`, `exceptionstatus`, `screws` 같은 시스템 데이터를 marker 색상, 팝업, 탭, 로그, 말풍선으로 변환하여 사용자가 즉시 이해할 수 있는 UI로 표현했습니다. 웹은 단순 표시층이 아니라 시스템 상태를 사람이 이해할 수 있게 번역하는 계층이라는 점을 배웠습니다.

### 4. 통합 프로젝트에서는 DB 경로 합의와 UI 상태 제어가 핵심이다

- **문제 인식**: 비전, 로봇, 웹 파트가 서로 다른 데이터 구조를 기준으로 개발하면 화면 표시와 실제 로봇 제어가 어긋날 수 있습니다.
- **배움과 극복**: `live_scan/workstations`를 기준으로 작업대, 배경 Point Cloud, 나사 상태를 통합하고, DB key는 유지하면서 화면 번호만 보정하는 방식으로 호환성과 UX를 함께 확보했습니다. 이를 통해 Web / Integration 파트에서 데이터 구조 합의와 상태 제어의 중요성을 체감했습니다.

## ✅ 최종 정리

KJH의 Web / Integration 파트는 JoinGo 프로젝트에서 로봇·비전·DB 데이터를 사용자가 실제로 이해하고 조작할 수 있는 웹 대시보드로 전환하는 역할을 수행했습니다.

초기에는 Firebase 검사 결과를 표시하는 단순 모니터링 화면이었지만, 이후 3D Scan Viewer, 작업대별 스캔 결과 선택, Point Cloud 샘플링, 나사별 상세 로그 팝업, 불량 해결 처리, 예외 상황 대응, RGB 영상 탭, 메인 애니메이션까지 통합된 관제 UI로 확장되었습니다.

특히 실시간 3D 렌더링으로 인한 렉 문제를 `3d_scan_done` 완료 게이트와 샘플링 레이트 선택 구조로 완화했으며, 작업대별 스캔 결과와 나사별 상태를 웹에서 직접 확인할 수 있도록 구성했습니다.

최종적으로 JoinGo 웹페이지는 단순한 화면 구현을 넘어, 자동 나사 체결 상태 점검 및 대응화 시스템에서 로봇 상태·3D Scan 결과·DB 상태·사용자 대응을 연결하는 핵심 통합 인터페이스로 완성되었습니다.
